## 一、基线数据口径（最优先）

> **官方规则原文**（赛道一精度约束，源自官方公众号 / MindSpore 活动页）："在 Daily-Omni、TTS-Seed、Video-MME 等 Benchmark 上，优化后相对**对应框架基线**的精度降幅不超过 2 个百分点。"

**Q1.** 依上述"**对应框架基线**"口径，子赛道 A 的基线应为 **llama.cpp-omni 框架自身**的实测成绩。烦请确认：评测规范中所列 Daily-Omni 基线 **79.5**、VideoMME 基线 **69.0**，是否即 **llama.cpp-omni 框架的实测基线**？分两种情况：

- **若是**：我队实测 Daily-Omni 仅约 **6.7%–12.5%**、VideoMME 尚未跑通，与基线差距达 60+ 个百分点（远超"降幅 ≤2pp"）。鉴于 omni 框架存在若干**框架级硬限制**（详见第四部分佐证：whisper 30s 窗口、单帧视觉、thinking 输出），烦请提供**官方推荐的 omni 框架运行配置**，以厘清该巨大 gap 是否源于配置差异。
- **若否**（即 79.5/69.0 实为原生 MiniCPM-o / Qwen-Omni 等非 omni 框架成绩——规范自注"公开 leaderboard 的 Qwen 61.82 属另一框架"亦印证此可能）：烦请**提供 llama.cpp-omni 框架的实测基线**，或对这两项准入阈值作相应调整，以符合"对应框架基线"的规则口径。

## 三、官方评测脚本与方法

**Q4.** 官方 `llama.cpp-omni` benchmark **评测脚本**计划何时、在何处发布？目前我队仅有 Daily-Omni / TTS-Seed 的**参考移植**（自 vllm-omni 口径），**VideoMME 暂无官方脚本**（现用脚本为我队自行编写）。

**Q5.** **VideoMME** 的官方评测方法是什么？特别是：长视频如何处理（分片 / 抽帧）、使用何种 prompt、答案如何抽取？

**Q6.** Daily-Omni / VideoMME 评测的**接入方式**：是直连 omni server 的 WebSocket（`/v1/worker/duplex`），还是经由 gateway？是否指定 system_prompt？评测为**全量**（Daily-Omni 1196 条 / VideoMME 2700 题）还是抽样？

## 四、框架限制与合规跑法（佐证材料）

我队在 omni 框架上实测 Daily-Omni / VideoMME 时，观察到以下**框架级限制**，致使精度远低于所列基线，特附上供组委参考：

1. **Whisper 30s 音频窗口**：omni 音频前端按标准 whisper 30s 窗口工作；Daily-Omni 样本约 **96.7% 音频 > 30s**（半数 60s），超长部分被截断，**音频信息丢失近半**。
2. **单帧视觉限制**：omni 在 turn_based 模式下，输入多帧视觉 embedding（≥ 2 帧）会触发**模型退化 / 重复输出**（输出退化为重复不可打印 token）。因此只能采用**单帧视觉**，对视频类 benchmark 的信息覆盖严重不足。
3. **输出风格**：模型在多模态 QA 下倾向 thinking 风格输出，常不直接给出明确的 ABCD 选项，影响答案抽取。
4. **VideoMME 稳定性**：处理 VideoMME 较大视频文件时 server 静默崩溃，尚未定位（见 Q5）。

**Q7.** 针对上述限制，**官方推荐的 omni 框架运行 Daily-Omni / VideoMME 的配置是什么**？是否**允许框架级适配**（如音频分段、视觉帧数控制、输出格式约束等）以规避这些限制？或是否有官方指定的处理方式？
